# M5 results: live analysis

Measured 2026-10-17 on this laptop with the retrained M4 student (441 tracks, 96 channels, lookahead 2 frames; docs/results/M4.md) and the section rules of adf76b5. Reproduce from the repository root with `app\build\windows-msvc\release\psyight_live_check.exe data\<track>`.

`psyight_live_check` feeds the decoded mix to the live analysis (`app/src/analysis/live_analysis.*`) in 480-sample blocks, as WASAPI delivers them. It compares the result with the file-mode analysis of the same audio: stems when they exist, on the labelled grid. Live mode is strictly causal and never sees the stems.

The cost is the share of one core over the whole track. Per 10 ms block: median 112 to 184 µs, p99 about 250 µs, and the worst block 4 to 10 ms. Decision latency is measured from the audio a decision describes: kicks 16.0 ms, bass onsets 26.7 ms, plus up to one 5.3 ms hop. The beat phase is predicted, so it adds no latency once locked.

## What the numbers say

- **Causal decoding costs nothing measurable.** On the labelled minute, live bass scores F 0.991, the file-mode student's score, 0.003 below file-mode DSP; live and file-mode student notes agree at F 0.998 to 1.000.
- **Section rules, refined on the trace** (`psyight_live_check --trace a b`): a run needs a bar of kicks (stray kick pairs inside a breakdown had made runs); a second detection on the same beat does not break a run; a run ends a breakdown whatever its gap. OculusDrift's sections now follow file mode's (breakdowns at 179 and 197 s, the drop at 240 s, groove at 253 s), with one false 3 s breakdown at 26 s where the student hears off-beat kicks.
- **The beat loop is accurate where the kick is clear.** On OculusDrift and Phase Change, 98 to 100% of checks fall within 20 ms of the file grid.
- **Bar position is the weak point.** Live mode takes the downbeat from a run of kicks returning after a break.
  - Bar-level novelty (file mode's cue for tracks without breaks) was tried as an override. On OculusDrift, whose grid is labelled by ear, it turned correct break downbeats wrong for long stretches: 90% fell to 77%. It now only replaces the arbitrary phase of the first lock, until the first break.
  - OculusDrift's remaining errors (440 checks one beat off) all come before its first break.
  - Phase Change: live mode, from a kick break, is consistently 3 beats from the drafted labelled grid (3577 of 4914 checks). That is the same disagreement the file-mode mix analysis has with the stems analysis the draft came from. Two independent mix-based cues agree, so the drafted downbeat is probably wrong. Listen to it before using that grid's bar numbers [Verify].
  - Hall of Purity and Hagios: the offsets spread over all four phases; their live kicks are unreliable (below).
- **Hall of Purity's kicks are distorted** (click ratio 0.19, SPEC 6.4). The student finds only 57% of the file-mode kicks there, but the loop still locks: phase |median| 2.1 ms.
- **Hagios is mostly beatless** (441 file-mode kicks in 17 minutes) and the student fires on other sounds: 1060 live kicks. With the live range up to 200 BPM (190 clamped it), the loop wanders to 192.8 BPM: on this mostly beatless track the student's kicks are too unreliable (precision 0.23) to steer it. The file grid is 189.1. `psyight_analyse --tempo data\Hagios.mp3` shows the tempo is not constant: per minute it runs from 186.6 to 189.4 BPM, and the mix estimate is 187.65, near the owner's "about 187". The drafted labelled grid (189.128, from the stems analysis) is constant, so it drifts against the music. This row therefore measures the reference as much as live mode. A constant-tempo grid cannot describe this track; the live loop, which follows the tempo, may be closer [Verify by ear].
- **Sections:** with kicks counted only in runs, OculusDrift's live sections follow file mode's: breakdowns at 179 and 197 s, the drop at 240 s, groove at 253 s. A breakdown is known 2 bars after it starts (about 3 s), as the rule needs. Outros cannot be told from breakdowns causally.

## In the app

The Preview panel's "Live input" section starts WASAPI loopback (whatever this computer plays) or any input device, and pauses the file. The show then renders from the live analysis, on the live clock. The section shows lock, tempo, beat, section, analysis delay, load, level and dropped samples, and has a tap test that can set the latency offset.

Checked with loopback, nothing playing: it starts, listens, reports a 13 ms analysis delay, and stops. Loopback delivers no samples while nothing plays, so the analysis thread fills such gaps with silence and the live clock keeps time.

Not yet checked: a real DJ set through loopback or an interface. That is the M5 exit, and it needs music playing out loud, so it is the owner's test. End-to-end latency to the LEDs needs the node and a light sensor or camera.

## MIDI

The Preview panel's MIDI section picks a controller (RtMidi 6.0.0, MIT) and learns bindings for blackout, hold, automation, each scene, the brightness cap, the latency offset and the tap test. Buttons fire on a note on or on a controller crossing the middle (a toggle or a pad); the brightness cap and latency offset follow a controller. Bindings and the port are saved in the project file. The mapping is tested (`psyight_tests -tc="midi*"`); this laptop has no MIDI input, so a real controller is untested.
