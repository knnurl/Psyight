# M5 results: live analysis

Measured 2026-10-17 on this laptop with the M4 baseline student (`data/m4/student.weights`, 96 channels, lookahead 2 frames). Reproduce from the repository root with `app\build\windows-msvc\release\psyight_live_check.exe data\<track>`.

`psyight_live_check` feeds the decoded mix to the live analysis (`app/src/analysis/live_analysis.*`) in 480-sample blocks, as WASAPI delivers them. It compares the result with the file-mode analysis of the same audio: stems when they exist, on the labelled grid. Live mode is strictly causal and never sees the stems.

The cost is the share of one core over the whole track. Per 10 ms block: median 112 to 184 µs, p99 about 250 µs, and the worst block 4 to 10 ms. Decision latency is measured from the audio a decision describes: kicks 16.0 ms, bass onsets 26.7 ms, plus up to one 5.3 ms hop. The beat phase is predicted, so it adds no latency once locked.

## What the numbers say

- **Causal decoding costs almost nothing.** On the labelled minute, live bass scores F 0.980 against the file-mode student's 0.981.
- **The beat loop is accurate where the kick is clear.** On OculusDrift and Phase Change, 98 to 100% of checks fall within 20 ms of the file grid.
- **Bar position is the weak point.** Live mode finds the downbeat only where a run of kicks returns after a break. Phase Change has no break, so its bar phase stays where the loop first locked (25%: chance). File mode falls back to bar-level novelty; live mode needs the same cue. Not built yet.
- **Hall of Purity's kicks are distorted** (click ratio 0.19, SPEC 6.4). The student finds only 57% of the file-mode kicks there, but the loop still locks: phase |median| 2.1 ms.
- **Hagios is mostly beatless** (441 file-mode kicks in 17 minutes) and the student fires on other sounds: 1060 live kicks. The loop settles at 186.2 BPM against the file grid's 189.1. The owner's estimate is about 187, so the constant-tempo file grid may be the one that is wrong on this track [Verify]. A per-minute tempo comparison (`psyight_analyse --tempo`) is the next check.
- **Sections:** with kicks counted only in runs, OculusDrift's live sections follow file mode's: breakdowns at 179 and 197 s, the drop at 240 s, groove at 253 s. A breakdown is known 2 bars after it starts (about 3 s), as the rule needs. Outros cannot be told from breakdowns causally.

## In the app

The Preview panel's "Live input" section starts WASAPI loopback (whatever this computer plays) or any input device, and pauses the file. The show then renders from the live analysis, on the live clock. The section shows lock, tempo, beat, section, analysis delay, load, level and dropped samples, and has a tap test that can set the latency offset.

Checked with loopback, nothing playing: it starts, listens, reports a 13 ms analysis delay, and stops. Loopback delivers no samples while nothing plays, so the analysis thread fills such gaps with silence and the live clock keeps time.

Not yet checked: a real DJ set through loopback or an interface. That is the M5 exit, and it needs music playing out loud, so it is the owner's test. End-to-end latency to the LEDs needs the node and a light sensor or camera.
